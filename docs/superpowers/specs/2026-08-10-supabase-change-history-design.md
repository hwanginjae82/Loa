# Supabase 변경 이력 보관 설계

## 목적

`raid_board_state`가 다른 사용자나 오래 열린 브라우저 화면에서 덮어써지더라도, 수정 직전 상태를 찾아 복구할 수 있게 한다. 현재 사이트의 편집 동작과 화면은 변경하지 않는다.

## 검토한 방식

1. **수정 직전 상태 자동 보관 — 선택**
   - 데이터베이스 트리거가 매번 `OLD` 값을 이력 표에 저장한다.
   - 사이트 코드를 거치지 않으므로 어떤 브라우저에서 수정해도 빠짐없이 기록된다.
2. 앱에서 저장할 때만 이력 보관
   - 구현은 단순하지만 오래된 앱이나 다른 저장 경로가 이력 저장을 건너뛸 수 있다.
3. Supabase 유료 백업/PITR 사용
   - 운영은 편하지만 무료 플랜에서는 사용할 수 없고 비용이 크다.

## 데이터 구조

새 표 `public.raid_board_state_history`를 만든다.

- `history_id`: 기록 순번
- `state_id`: 원본 상태 ID (`guild-main`)
- `members`, `catalog`, `schedule`: 수정 직전 전체 데이터
- `source_updated_at`: 원본 데이터가 마지막으로 저장됐던 시각
- `archived_at`: 이력으로 보관된 시각

이력 표에는 RLS를 켜고 익명 사용자 및 일반 로그인 사용자에게 권한을 주지 않는다. 사이트는 이력 표를 읽거나 수정할 필요가 없다.

## 저장 흐름

1. 사이트가 기존처럼 `raid_board_state`를 수정한다.
2. 데이터베이스의 `BEFORE UPDATE` 트리거가 실행된다.
3. 트리거가 수정 직전 전체 행을 이력 표에 추가한다.
4. 원래 수정이 정상적으로 진행된다.

이력 저장이 실패하면 원래 수정도 취소되어, 기록 없이 데이터만 덮어써지는 상황을 막는다.

## 복구 방식

관리자가 Supabase에서 이력의 `archived_at`과 내용을 확인한 뒤, 선택한 기록의 `members`, `catalog`, `schedule`을 `raid_board_state`에 다시 적용한다. 복구 자체도 하나의 수정이므로 복구 직전 상태가 다시 이력에 남는다.

## 적용 안전성

- `CREATE ... IF NOT EXISTS`와 트리거 재생성 방식으로 여러 번 실행해도 중복 트리거가 생기지 않게 한다.
- 기존 `raid_board_state`의 RLS 정책과 편집 권한은 이번 작업에서 변경하지 않는다.
- 적용 전 현재 `guild-main` 행을 별도 파일로 한 번 더 백업한다.
- 적용 후 시험용으로 데이터를 바꾸지 않는다. 대신 트리거와 표가 존재하는지 데이터베이스에서 확인하고, 다음 정상 저장 이후 이력 행이 생성되는지 확인한다.

## 이번 작업에서 제외

- 관리자 로그인 및 익명 쓰기 차단
- 동시에 편집할 때 충돌을 알려주는 버전 검사
- 이력 조회/복구 관리 화면
- 이력 자동 삭제 정책

이 항목들은 현재 사이트 동작을 바꿀 수 있으므로 별도 작업으로 진행한다.
